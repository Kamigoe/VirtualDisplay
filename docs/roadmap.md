# 今後の展望（候補と検討メモ）

2026-11-10 時点の候補。優先順位は未確定。実装に入るときは、ここから個別の計画書に切り出すこと。

## 1. 他のモニターへの対応（4K 60Hz、FHD 240Hz など）

仕組みはすでにある：`vdview` はモニターの解像度・スケール・リフレッシュレートを Mac に伝え、
エンコーダの上限（約 650 Mpx/s、`ENCODER_PIXEL_RATE`）を超えるとリフレッシュレートを下げる。
残りは「実機で確かめること」と「既定の決め方」。

| モニター | 画素レート | 検討点 |
|---|---|---|
| 4K 60Hz | 498 Mpx/s | HiDPI の判定が「スケール 175% 以上」なので、150% の 4K（この PC の DISPLAY2）だと Mac は 3840x2160 の等倍になり文字が小さい。150% 相当（2560x1440 HiDPI）は描画が 5120x2880 になり 885 Mpx/s で上限超え。1920x1080 HiDPI（200%）が現実的。判定の閾値か、モニターごとの既定を見直す |
| FHD 240Hz | 498 Mpx/s | 画素レートは上限内。macOS は 240Hz の仮想モニターを作れるが、取り込める fps は 120Hz のときより少なかった（下記の実測） |
| UWQHD 165Hz | 817 Mpx/s | 現状どおり 120Hz に下げる（確認済み） |

### 実測（2026-11-12、Wi-Fi、4:4:4、Mac 側の画面は普段の作業画面のまま）

測定中は、普段使いの `vdview` を閉じること。受信側は 1 台までなので、2 つの `vdview` が
2 秒ごとの自動再接続で接続を奪い合い、どちらも映らなくなる（実際に起きた）。

**4K 60Hz（この PC の DISPLAY2、スケール 150%、全画面）**

| 設定 | Mac 側 | fps | 遅延 p50 / p95 |
|---|---|---|---|
| 既定（150% → 等倍） | 3840x2160 pt / 3840x2160 px | 57 | 27.4 / 38.1 ms |
| `--hidpi` | 1920x1080 pt / 3840x2160 px | 57 | 25.6 / 31.2 ms |

どちらも Mac は要求どおりに切り替わり、欠落なし。
→ 既定は今のまま（175% 未満は等倍）とし、表示中に **F5 で HiDPI ⇔ 等倍を切り替えられる**ようにした
（実解像度は同じなので、リフレッシュレートの上限も変わらない。切替は約 1 秒）。起動時に決めるなら `--hidpi` / `--no-hidpi`。

**FHD の高リフレッシュレート（`--mode 1920x1080@HZ`、ウィンドウ表示、240Hz のモニターなし）**

| 要求 | Mac の仮想モニター | capture / encode fps（Mac） | enc p50 | vdview の fps 中央値 | 遅延 p50 |
|---|---|---|---|---|---|
| 120Hz | 120 Hz | 65〜108 | 6.3 ms | 103 | 10.0 ms |
| 144Hz | 144 Hz | 95〜110 | 6.0 ms | 102 | 9.7 ms |
| 165Hz | 165 Hz | 66〜100 | 6.0 ms | 89 | 10.1 ms |
| 180Hz | 180 Hz | 85〜104 | 6.0 ms | 102 | 10.0 ms |
| 240Hz | 240 Hz | 45〜68 | 6.6 ms | 55 | 12.4 ms |
| 240Hz 4:2:0 8bit | 240 Hz | 25〜87 | 7.5 ms | 52 | 11.6 ms |

- macOS は 240Hz まで受け付ける（`virtual display 3: ... @ 240.0 Hz`）。`ControlServer` も 240Hz まで許可している。
- capture と encode の fps は常に一致しており、エンコーダは追いついている（FHD 4:4:4 で 6ms）。
  **頭打ちの原因は取り込み側**（ScreenCaptureKit が渡すフレーム数）。
- 取り込みは画面が変化したときだけ届くので、fps は画面の内容次第。普段の作業画面では、120〜180Hz で
  約 100〜110fps、**240Hz ではかえって 45〜68fps に下がった**。WindowServer か画面上のアプリが 240Hz の
  仮想モニターでは描画を間引いているように見えるが、内容を固定した試験（全画面のアニメーション等）でないと断定できない。
- 当面の判断：240Hz を要求すると 120Hz より悪くなるので、モニターに合わせるときは **120Hz を上限にした**
  （`MAX_REFRESH_MHZ`。`--mode` で明示した場合は上限なし）。240Hz を活かすには、内容を固定した試験で原因を突き止める必要がある。

**遅延についての手がかり**

- FHD では遅延が約 10ms で、UWQHD・4K（26〜36ms）の 3 分の 1 ほど。
- FHD では Mac 側の composite→encoded（p95 約 8.5ms）と vdview の net（p95 約 11ms）の差は約 2.5ms。
  UWQHD（11/10 の測定、50 Mbps）では net p95 が約 35ms、Mac 側の composite→encoded p95 が約 17ms
  （11/12 のログ）で、差が約 18ms ある。
- `vdsend` はフレームを間隔を空けずに一度に送る。大きいフレームほど Wi-Fi で送り終えるまで時間がかかるので、
  高解像度の遅延の約半分は転送時間ではないかと考えられる（仮説。同じ内容・同じ日に Mac と PC の両方の数字を取って確かめる）。
  確かめられれば、ビットレートを下げる、Mac を有線にする、といった対策の効果が見積もれる。

**その他**

- Windows で一度だけ `udp receive error: ... (os error 997)`（ERROR_IO_PENDING）が出て、1 フレーム欠けた。
  すぐに回復した。頻発するようなら、`receiver.rs` で一時的なエラーとして扱う。
- Mac の名前（`.local`）から IPv4 が引けないことがあり、そのとき `vdview` は IPv6 のリンクローカルアドレスで
  接続していた。動作に問題はない。

## 2. 既存ツールとの統合

### my-vnc（Mac → Windows の画面キャスト、ffmpeg + mpv）

機能は VirtualDisplay がほぼ上回る（仮想モニター、HEVC 4:4:4 / 10bit、再送つき UDP、
受信側モニターへの自動追従、自動起動）。移植したい機能は見当たらないため、
**VirtualDisplay に一本化し、my-vnc は役目を終える**のが自然。
参考にする価値があるのは、設定ファイル（`config.example.*` を配布し、実体は .gitignore）の運用くらい。

### mac-input-cast（Windows → Mac の入力キャスト、Python）

統合の効果が大きい。`vdview` に入力の送信を組み込めば、mac-input-cast の制約がいくつか解ける。

| mac-input-cast の制約 | vdview に組み込んだ場合 |
|---|---|
| マウスは相対移動のみ | `vdview` はウィンドウ座標と Mac の仮想モニターの座標の対応を知っているので、絶対座標で送れる |
| Mac のメインディスプレイのみ | `vdsend` が仮想モニターの ID を持っているので、そのモニターに正しく注入できる |
| Ubuntu 非対応 | winit のキー入力（`KeyCode`、物理キー）は Windows / Ubuntu 共通。`Convert` / `NonConvert` / `KanaMode` もある |
| 別プロセス・別接続 | 映像と同じ制御用 TCP に乗せられる（入力は少量なので帯域は問題にならない） |

流用できるもの：JIS 前提のキー対応表（`VK_TO_MAC`）、IME 切替の割り当て（無変換 → 英数、変換 → かな、
半角/全角 → トグル）、修飾キーの対応（Ctrl → Command など）と変更オプション、転送のオン/オフ切替（F8）。

決めること・注意点：

- **README の「映像専用（入力の逆送はしない）」という前提が変わる。**
- **認証が必須になる。** 入力の注入は遠隔操作の入口そのもの。現状の制御チャネルは LAN 内で無認証なので、
  共有シークレット（mac-input-cast の `--token` 相当）以上の認証を入れる。
- Mac 側は `vdsend.app` に「アクセシビリティ」の許可が要る。署名が固定（`make-signing-identity.sh`）なので、
  再ビルドしても許可は外れないはず。`CGEventPost` は Swift から直接呼べる（Apple 純正のみの方針を保てる）。
- F1〜F4 / F11 / Esc は `vdview` 自身の操作に使っているので、転送中の扱い（切替キーで分ける等）を決める。
- 実装は Rust（vdview）と Swift（vdsend）で書き直しになる。Python 版は動作の参考として使う。

## 3. クリップボードの共有、カーソルの共有（D&D を含む）

入力の統合（2.）が土台になるので、その後に検討する。

- **カーソルをローカルで描く**（遅延対策として効果大）：今は Mac 側でカーソルを映像に焼き込んでいる
  （`Capture.swift` の `showsCursor = true`）。入力を統合して絶対座標で送るなら、PC 側でカーソルを
  即座に描けるので、20〜30ms の遅延があっても操作感がかなり良くなる。カーソルの形（矢印・I ビーム等）は
  Mac から変化時だけ送る。
- **テキストのクリップボード**：制御用 TCP に載せる。Mac は `NSPasteboard` の `changeCount` を監視、
  Windows は Win32 のクリップボード API を直接宣言して使える（依存を増やさない方針を保てる）。
  Ubuntu（X11 / Wayland）は依存なしだと手間が大きいので、方針の見直しが必要かもしれない。
  画像やファイルは後回し。
- **D&D・画面端でのカーソル移動**（Universal Control のような使い方）：モニター間のカーソル移動の判定、
  ファイル転送、両 OS の D&D API が絡み、規模が大きい。最後に検討。
