# 今後の展望（候補と検討メモ）

2026-11-10 時点の候補。優先順位は未確定。実装に入るときは、ここから個別の計画書に切り出すこと。

## 1. 他のモニターへの対応（4K 60Hz、FHD 240Hz など）

仕組みはすでにある：`vdview` はモニターの解像度・スケール・リフレッシュレートを Mac に伝え、
エンコーダの上限（約 650 Mpx/s、`ENCODER_PIXEL_RATE`）を超えるとリフレッシュレートを下げる。
残りは「実機で確かめること」と「既定の決め方」。

| モニター | 画素レート | 検討点 |
|---|---|---|
| 4K 60Hz | 498 Mpx/s | HiDPI の判定が「スケール 175% 以上」なので、150% の 4K（この PC の DISPLAY2）だと Mac は 3840x2160 の等倍になり文字が小さい。150% 相当（2560x1440 HiDPI）は描画が 5120x2880 になり 885 Mpx/s で上限超え。1920x1080 HiDPI（200%）が現実的。判定の閾値か、モニターごとの既定を見直す |
| FHD 240Hz | 498 Mpx/s | 画素レートは上限内だが、1 フレームの時間が 4.2ms。M1 のエンコード時間（FHD 4:4:4 で p50 約 7ms）はこれを超えるので、パイプラインで処理量が追いつくかは要測定。`CGVirtualDisplay` と ScreenCaptureKit が 240Hz を出せるかも未確認 |
| UWQHD 165Hz | 817 Mpx/s | 現状どおり 120Hz に下げる（確認済み） |

`--monitor N` でモニターを選べるので、まずは各モニターで `vdview` を起動し、Mac 側のログ
（`virtual display ...: WxH pt, WxH px @ Hz`）と遅延の内訳を記録するところから。

## 2. 既存ツールとの統合

### my-vnc（Mac → Windows の画面キャスト、ffmpeg + mpv）

機能は VirtualDisplay がほぼ上回る（仮想モニター、HEVC 4:4:4 / 10bit、再送つき UDP、
受信側モニターへの自動追従、自動起動）。移植したい機能は見当たらないため、
**VirtualDisplay に一本化し、my-vnc は役目を終える**のが自然。
参考にする価値があるのは、設定ファイル（`config.example.*` を配布し、実体は .gitignore）の運用くらい。

### mac-input-cast（Windows → Mac の入力キャスト、Python）

統合の効果が大きい。`vdview` に入力の送信を組み込めば、mac-input-cast の制約がいくつか解ける。

| mac-input-cast の制約 | vdview に組み込んだ場合 |
|---|---|
| マウスは相対移動のみ | `vdview` はウィンドウ座標と Mac の仮想モニターの座標の対応を知っているので、絶対座標で送れる |
| Mac のメインディスプレイのみ | `vdsend` が仮想モニターの ID を持っているので、そのモニターに正しく注入できる |
| Ubuntu 非対応 | winit のキー入力（`KeyCode`、物理キー）は Windows / Ubuntu 共通。`Convert` / `NonConvert` / `KanaMode` もある |
| 別プロセス・別接続 | 映像と同じ制御用 TCP に乗せられる（入力は少量なので帯域は問題にならない） |

流用できるもの：JIS 前提のキー対応表（`VK_TO_MAC`）、IME 切替の割り当て（無変換 → 英数、変換 → かな、
半角/全角 → トグル）、修飾キーの対応（Ctrl → Command など）と変更オプション、転送のオン/オフ切替（F8）。

決めること・注意点：

- **README の「映像専用（入力の逆送はしない）」という前提が変わる。**
- **認証が必須になる。** 入力の注入は遠隔操作の入口そのもの。現状の制御チャネルは LAN 内で無認証なので、
  共有シークレット（mac-input-cast の `--token` 相当）以上の認証を入れる。
- Mac 側は `vdsend.app` に「アクセシビリティ」の許可が要る。署名が固定（`make-signing-identity.sh`）なので、
  再ビルドしても許可は外れないはず。`CGEventPost` は Swift から直接呼べる（Apple 純正のみの方針を保てる）。
- F1〜F4 / F11 / Esc は `vdview` 自身の操作に使っているので、転送中の扱い（切替キーで分ける等）を決める。
- 実装は Rust（vdview）と Swift（vdsend）で書き直しになる。Python 版は動作の参考として使う。

## 3. クリップボードの共有、カーソルの共有（D&D を含む）

入力の統合（2.）が土台になるので、その後に検討する。

- **カーソルをローカルで描く**（遅延対策として効果大）：今は Mac 側でカーソルを映像に焼き込んでいる
  （`Capture.swift` の `showsCursor = true`）。入力を統合して絶対座標で送るなら、PC 側でカーソルを
  即座に描けるので、20〜30ms の遅延があっても操作感がかなり良くなる。カーソルの形（矢印・I ビーム等）は
  Mac から変化時だけ送る。
- **テキストのクリップボード**：制御用 TCP に載せる。Mac は `NSPasteboard` の `changeCount` を監視、
  Windows は Win32 のクリップボード API を直接宣言して使える（依存を増やさない方針を保てる）。
  Ubuntu（X11 / Wayland）は依存なしだと手間が大きいので、方針の見直しが必要かもしれない。
  画像やファイルは後回し。
- **D&D・画面端でのカーソル移動**（Universal Control のような使い方）：モニター間のカーソル移動の判定、
  ファイル転送、両 OS の D&D API が絡み、規模が大きい。最後に検討。
